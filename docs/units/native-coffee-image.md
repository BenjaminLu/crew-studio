# Dedicated Codex image capability

Phase 1 scope approved by the captain via firstmate: src/providers/codex-image.ts,
tests/codex-image.ts, tests/codex-image-fixture.mjs, package.json and this file.
src/providers/needs.ts may change only for dedicated sandbox needs if required;
ordinary Codex provider flags and existing model/account choices remain intact.
Base: 1420bdf. No HTTP route or automatic tutorial activation in this phase.

Build a source-owned image-only app-server turn with the existing verified
account and approved model/effort, no fallback. The installed stable protocol
provides thread/start, turn/start, item/completed imageGeneration with
status/result/savedPath/failure, and turn/completed. CLI app-server --help
supports --enable/--disable feature and -c overrides. Feature presence and
schema do not prove actual account image entitlement.

The process uses a private allowlisted login copy, OS round sandbox and owned
egress proxy; no user config, hooks, shell, web or model-provided tools. Source
authority and cancellation are checked before and after asynchronous admission,
before model launch and before returning an output. Only one completed image
and a successful matching thread/turn may produce verified bytes. No text-only
success, malformed/partial image or arbitrary output path is accepted.

Validate bounded PNG structure, CRC, decoded byte count and dimensions. Import
only exact owned generated-file paths or validated event bytes; stop the owned
process group before exposing output and deleting the disposable auth home.
Unverified teardown retains the home and returns a bounded capability failure.
Never persist raw RPC/auth responses in reports. No actual source login changes.

Strict fixtures cover success and all refusal classes, process deadlines,
cancel during admission/turn, wrong IDs, unsafe paths/symlinks and fake image
bytes. Meaningful old-source control uses the ordinary provider with a genuine
image-completion fixture: it must not be advertised as an image-producing
adapter. Missing-module failures are not behavioral fail-first evidence.

After fixtures pass, the authorized real canary generates one coffee-shop
image only, with configured verified model/account, owned output and bounded
deadline. A refusal remains a capability HOLD, not a fake image success.
HyperFrames and integrated whole-site review are subsequent separate units.
